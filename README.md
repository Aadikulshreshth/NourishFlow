# RescueRoute

**A Multi-Agent Food Rescue and Allocation Optimization System**

RescueRoute is a student proof of concept for coordinating surplus food donations with community recipients. It allocates eligible food under supply, demand, storage, urgency, compatibility, expiry-window and recipient-deadline constraints. It is designed to be explainable and testable, with a Streamlit UI and downloadable outputs.

> **Safety scope:** Synthetic data is used by default. This is not an operational food-safety, dispatch, or donor/recipient verification system. Qualified people must verify food safety, handling conditions, eligibility and real delivery decisions.

## Current milestone

Implemented:
- Deterministic Data Intake, Planner, Allocation Optimizer, Critic, Correction and Report stages.
- Mixed-integer linear optimization using `scipy.optimize.milp`; allocations are whole kilograms.
- Constraint checks for supply, recipient demand, storage capacity, accepted food types and estimated delivery windows.
- Conditional input rejection for invalid schemas and malformed values.
- Reproducible scenarios: baseline, time-critical food, donation disruption, supply shortage and invalid input.
- Critic fault injection that deliberately corrupts a plan, demonstrates rejection, and triggers one correction/retry.
- Streamlit dashboard with metrics, allocations, execution logs, and CSV downloads.
- Automated tests for baseline output, capacity constraints, invalid input, correction/retry and disruption behavior.

Next milestone:
- Add OR-Tools route optimization with vehicle capacities and time windows.
- Replan when vehicles or donations become unavailable.
- Compare optimized plans against a simple baseline and report quantitative performance.

## Scenarios to demonstrate

1. **Baseline:** the optimizer allocates available food to compatible recipients while observing capacity and time constraints.
2. **Time-critical food:** a short food window and delivery deadline alter the set of eligible allocation links.
3. **Donation disruption:** one donation is removed and the optimizer rebuilds the plan with the remaining supply.
4. **Supply shortage:** donation quantities are reduced, making unmet demand visible.
5. **Invalid input:** a required quantity column is removed, so Intake rejects the data.
6. **Critic + retry:** enable fault injection; the Critic rejects an intentionally corrupted plan, and the Correction Agent reruns optimization from the original data.

## CSV schemas

### Donations
`donation_id`, `donor_name`, `food_type`, `quantity_kg`, `expiry_hours`, `x_km`, `y_km`, `available`

### Recipients
`recipient_id`, `recipient_name`, `demand_kg`, `storage_capacity_kg`, `urgency`, `delivery_deadline_hours`, `accepts_food_types`, `x_km`, `y_km`

`accepts_food_types` is a pipe-separated string, for example `Produce|Grains|Prepared meals`. Coordinates are synthetic local-grid kilometres. The optimizer estimates a delivery time as a fixed handling buffer plus Euclidean distance divided by a configured average speed; this is a simplifying assumption, not live travel-time data.

## Technical note

The agents in this milestone are deterministic Python components, not LLM-driven autonomous agents. Their agentic properties demonstrated here are conditional task planning, tool execution, state passing, validation, rejection, correction and retry. Numerical decisions are computed using a mixed-integer optimizer rather than generated by an LLM.
